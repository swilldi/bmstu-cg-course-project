# NOTES — заметки, кандидаты, открытые вопросы

## Кандидаты метода синтеза занавеса (для сравнительной таблицы этапа анализа)

Черновик, предложенный при подготовке заготовки — не обязателен к реализации всех трёх,
для РПЗ достаточно описать их в общем виде на этапе анализа, сравнить по критериям
(производительность / память / визуальное правдоподобие / простота параметризации под
входные данные ТЗ) и реализовать один. Проверить и поправить перед тем, как переносить в
`docs/SPEC.md`/анализ как окончательное.

1. **Слоистый шум** (Perlin/Simplex по высоте и времени). Быстро, дёшево по памяти,
   складчатость и протяжённость — это в чистом виде частота/октавы/масштаб шума, seed —
   это и есть сид генератора шума. Вероятно, лучший кандидат по простоте параметризации.
2. **Гармоническая модель** (сумма синусоид с фазовым сдвигом по времени, амплитуды и
   частоты рандомизированы по seed). Ещё дешевле шума, зато математически прозрачно
   объясняется в РПЗ и легко считать количественные характеристики (что хорошо ложится
   на требование методички к количественным критериям сравнения).
3. **Лёгкая частичная симуляция** (по seed раскидывается несколько «нитей»-сплайнов,
   каждая колеблется во времени независимо, занавес — их объединение). Визуально
   интереснее первых двух, дороже по вычислениям и сложнее параметризовать одним набором
   чисел из ТЗ.

## Открытые вопросы

- Подсветка сцены сиянием через 8–16 сэмплов-«пробников» вдоль занавеса как
  доп. точечные источники (см. `ARCHITECTURE.md`) — рабочая гипотеза, не проверена на
  перфомансе и на глаз. Если не устроит — менять только внутри общего lighting-model
  modifier.
- ~~Механизм SceneKit «тень от движка, использование света и тени — своё»~~ — проверено по
  документации Apple, точные структуры и условие (`shadowMode == .forward`) зафиксированы в
  `ARCHITECTURE.md`. Закрыто.
- `SCNShadable`/`SCNShaderModifierEntryPoint`/`SCNProgram` в документации Apple помечены
  Deprecated на всех платформах (доступны по факту до текущей версии SDK). Для курсовой не
  проблема — альтернативы с нужным уровнем контроля над освещением у RealityKit нет — но
  готовый ответ на возможный вопрос комиссии на защите держать в голове (см.
  `ARCHITECTURE.md`, последний абзац раздела «Механизм»).
- Источник карты высот: пока предполагается готовый grayscale-ассет в бандле, без
  редактора/процедурной генерации в рантайме. Если понадобится процедурный ландшафт —
  это отдельная функция-загрузчик, не трогает `Terrain` дальше загрузки.
- Нужен ли отдельный экран для `ResearchHarness` или хватит скрытого /debug-режима в
  существующем GUI — решить на технологическом этапе, когда будет с чем сравнивать по
  затратам на реализацию.
