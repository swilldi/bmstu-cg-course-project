# ARCHITECTURE — модули и баланс движок/вручную

Руководитель задал требование словами: «полностью самому — сложно, полностью через движок —
не выше 2–3». Поэтому архитектура явно разделяет, что отдаётся SceneKit, а что пишется
руками. Это разделение защищается и в технологическом разделе РПЗ.

## Кто что делает

| Часть | Источник | Почему так |
|---|---|---|
| Меш ландшафта (карта высот → геометрия) | движок (`SCNGeometry`) | декорация, не предмет курсовой |
| Пять объектов сцены (стандартные тела) | движок (`SCNSphere`/`SCNBox`/`SCNCylinder`/... + `segmentCount` как полигональная аппроксимация) | окружение, не ядро темы |
| Камера | движок (узел камеры + `SCNCameraController`/`allowsCameraControl`) | навигация, не графический алгоритм |
| Тень — построение карты теней | движок (`SCNLight.castsShadow`) | техническая генерация карты; как тень входит в освещение — своё |
| Модель освещения — диффузная и зеркальная составляющие, применение тени | **вручную** (custom lighting-model shader modifier) | заменяет стандартную модель отражения движка |
| Сияние — процедурный синтез занавесов | **вручную полностью** (`AuroraSynthesis`, Strategy: основания — CPU, заполнение сетки — compute-шейдер Metal) | ядро темы курсовой |
| Сияние — объёмный рендер (ray march) | **вручную полностью** (`SCNProgram`) | ядро темы курсовой |
| Подсветка сцены сиянием | **вручную полностью** (в том же lighting-model modifier, источники — свой массив, не `SCNLight`) | ядро темы курсовой |

Движку отдано то, что не является содержанием работы: геометрия окружения, навигация,
генерация карты теней. Всё, что составляет тему — синтез, объёмный рендер, уравнение
освещения и то, как в него входят тень и свечение, — написано руками.

## Механизм: тень от движка, освещение — вручную

У SceneKit слоёная система кастомизации шейдера: geometry → surface → **lighting model** →
fragment (`SCNShaderModifierEntryPoint`); каждый слой переопределяется, не трогая соседние.
`lightingModel` выполняется один раз на каждый активный источник света и оперирует двумя
структурами (по документации Apple; в Metal те же поля, `vec3`/`vec4` → `float3`/`float4`):

```glsl
struct SCNShaderLightingContribution {
   vec3 ambient;
   vec3 diffuse;
   vec3 specular;
} _lightingContribution;

struct SCNShaderLight {
   vec4 intensity;   // цвет вклада света — при forward-тенях уже с учётом тени
   vec3 direction;   // направление от точки поверхности к источнику (L), view space
} _light;
```

плюс структура слоя `surface`:

```glsl
struct SCNShaderSurface {
   vec3 view; vec3 position; vec3 normal; vec3 tangent; vec3 bitangent;
   vec4 ambient; vec4 diffuse; vec4 specular; vec4 emission; vec4 multiply;
   vec4 transparent; vec4 reflective;
   float shininess; float fresnel;
   // + пары *Texcoord для каждого vec4-текстурного свойства
} _surface;
```

Модификатор читает `_light`/`_surface` и сам пишет в `_lightingContribution.diffuse` и
`.specular`: диффузная составляющая — из `_light.intensity` и `dot(normal, direction)`,
зеркальная — по Блинну — Фонгу через `_surface.view`; коэффициенты $k_d$, $k_s$, $n$ — из
`ParameterStore`. Стандартная модель отражения SceneKit в этом не участвует.

**Тень попадает в `_light.intensity` только при `shadowMode == .forward`:** SceneKit
встраивает результат сравнения с картой теней в `intensity` до вызова модификатора. Это
значение по умолчанию, но в коде оно выставляется явно и обосновывается в РПЗ. При
`.deferred` тень накладывается постпроцессом после `lightingModel`, и модификатор её не
видит.

Один и тот же модификатор подключён к ландшафту и ко всем пяти объектам — иначе освещение и
тени по сцене не согласованы.

**Оговорка для защиты:** `SCNShadable`, `SCNShaderModifierEntryPoint` и `SCNProgram` в
документации Apple помечены Deprecated, но доступны в текущем SDK. Для курсовой это не
блокер: API работает и даёт нужный уровень ручного контроля над освещением, тенями и
сиянием; у RealityKit такого низкоуровневого доступа к освещению нет.

**Оси:** в SceneKit вверх направлена Y, в формализации РПЗ — Z. Отображение задаётся в
одном месте и явно.

## Модули

```
ParameterStore   — единственный источник правды по всем пользовательским значениям
       │
       ├─▶ AuroraSynthesis (протокол + одна активная реализация)   [вручную]
       │        │
       │        ▼
       │   3D-текстура расчётной сетки (AuroraGrid)
       │        │
       ├─▶ Terrain (SCNGeometry из карты высот)             [движок]
       ├─▶ SceneObject × ≥5 (SCNSphere/SCNBox/...)           [движок]
       │        │                              ▼
       │        │                    Aurora-нода: SCNProgram,
       │        │                    ray march по AuroraGrid          [вручную]
       │        ▼
       │   общий custom lighting-model modifier                [вручную]
       │   (диффуз + зеркало + тень движка + источники сияния)
       │        │
       │        ▼
       │                  кадр в SCNView / SceneView
       │
       └─▶ SwiftUI-панель (текстовые поля/слайдеры) — читает и пишет ParameterStore напрямую

CameraController — узел камеры + встроенный контроллер SceneKit          [движок]
ResearchHarness  — фиксированная сцена, перебор шага интегрирования и
                    размера сетки, замер времени кадра, CSV              [вручную]
```

### `AuroraSynthesis` — точка замены метода

Основания занавесов (шум Перлина, не более 256 точек × 8 занавесов) считаются на CPU, в
Swift. Расчётную сетку по основаниям заполняет compute-шейдер Metal в 3D `MTLTexture`.
Полный CPU-проход по сетке 256×256×128 (≈8,4·10⁶ узлов × до 8 занавесов) каждый кадр не
даёт реального времени, а отказаться от сетки нельзя — её требует задание, и на её размере
построено исследование. Compute-проход кодируется в собственный command buffer из
`renderer.commandQueue` в `renderer(_:willRenderScene:atTime:)`; текстура отдаётся
материалу аврора-ноды через `SCNMaterialProperty`.

`AuroraGrid` — 3D-текстура сетки (максимум 256×256×128), единственный интерфейс между
синтезом и рендером. `CurtainParameters` — высота границ, протяжённость, складчатость,
seed, три цвета (низ/середина/верх) — на каждый из восьми возможных занавесов. Конкретная
сигнатура протокола `AuroraCurtainSynthesizing` определяется на этапе проектирования.

**Ничего за пределами модуля не знает, какая реализация протокола активна.** Аврора-нода
и GUI работают только с протоколом и с `AuroraGrid`. Шум Перлина можно заменить, например,
на гармоническую модель из аналитического раздела, не трогая остальной код.

### Аврора-нода — объёмный рендер сияния (`SCNProgram`, вручную)

Геометрия-контейнер (ограничивающий объём на все занавесы) с материалом, которому назначен
`SCNProgram` — полная замена вершинного и фрагментного шейдера. SceneKit здесь не считает
освещение, а только передаёт матрицы камеры/проекции и выполняет draw call. Фрагментный
шейдер трассирует луч через `AuroraGrid` и интегрирует излучение и поглощение вдоль луча
(без рассеяния). Шаг интегрирования и размер сетки — параметры исследования
(`ResearchHarness`).

### Общий custom lighting-model modifier — свет, тень, подсветка сиянием (вручную)

Один модификатор на материалах ландшафта и всех пяти объектов:

- направленный источник (направление/цвет/интенсивность — из `ParameterStore`) с тенью от
  движка; диффузная и зеркальная составляющие считаются в модификаторе;
- подсветка сиянием: каждый кадр основание каждого активного занавеса делится на четыре
  участка (m ≤ 32), каждый участок — точечный источник (центр яркости, интенсивность,
  средний цвет). Источники передаются в шейдер своим массивом (буфер/текстура), а **не**
  как `SCNLight`: SceneKit учитывает не более восьми источников на узел и лишние молча
  отбрасывает. Сумма по источникам — формула подсветки сиянием из РПЗ с множителем
  видимости $S_j = 1$. `lightingModel` вызывается один раз на каждый `SCNLight`, поэтому
  место, где считается сумма, выбирается так, чтобы она добавлялась ровно один раз.

### `Terrain` и `SceneObject` (геометрия — движок, шейдинг — общий модификатор)

- `Terrain`: карта высот (grayscale-изображение) → `SCNGeometry` с нормалями средствами
  SceneKit. Загрузчик карты высот — отдельная функция, заменяемая без правок построения
  геометрии.
- `SceneObject`: не менее пяти объектов из стандартных тел SceneKit
  (`SCNSphere`/`SCNBox`/`SCNCylinder`/`SCNCone`/`SCNTorus`), полигональная аппроксимация —
  параметр тесселяции примитива. Список объектов — данные (массив описаний:
  тип/трансформ/материал), а не россыпь вызовов в коде.
- Файл описания сцены задаёт состав, цвета и расстановку объектов и начальные коэффициенты
  отражения ландшафта и каждого объекта.

### `ParameterStore`

Один `@Observable`-объект со всеми пользовательскими значениями (список — `SPEC.md`),
включая коэффициенты отражения по каждой поверхности, которые инициализируются из файла
описания сцены. SwiftUI-панель читает и пишет его напрямую, рендер читает его на каждый
кадр.

### `CameraController` (движок)

Узел камеры + встроенный `SCNCameraController` SceneKit (или `allowsCameraControl` на
`SCNView`/`SceneView`) — орбита мышью, зум скроллом. Положение наблюдателя из текстовых
полей — запись в трансформ узла камеры из `ParameterStore` средствами SceneKit.

### `ResearchHarness` (вручную)

Фиксированная сцена, перебор (шаг интегрирования × размер сетки), замер времени кадра через
колбэки `SCNSceneRendererDelegate`, вывод в CSV. Анализ и графики — вне приложения.

## Потоки

Рендер живёт в колбэках `SCNSceneRendererDelegate`: один поток на кадр, GUI и ввод — main.
Структурированная конкурентность сверх необходимого не нужна.
