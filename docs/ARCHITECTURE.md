# ARCHITECTURE — модули и баланс движок/вручную

Требование руководителя не зафиксировано числом в ТЗ, но задано словами: «полностью
самому — сложно, полностью через движок — не выше 2–3». Значит архитектура должна явно
разделять, что отдаётся SceneKit, а что пишется руками — и это разделение важно не только
для кода, но и для технологического раздела РПЗ, где его придётся защищать.

## Кто что делает

| Часть | Источник | Почему так |
|---|---|---|
| Меш ландшафта (карта высот → геометрия) | движок (`SCNGeometry`) | чистая декорация, не предмет курсовой |
| Материал ландшафта (цвет/текстура снега) | движок | то же |
| Пять объектов сцены (стандартные тела) | движок (`SCNSphere`/`SCNBox`/`SCNCylinder`/... + `segmentCount` как полигональная аппроксимация) | окружение, не ядро темы |
| Камера | движок (узел камеры + `SCNCameraController`/`allowsCameraControl`) | навигация, не графический алгоритм |
| Тень — построение карты/depth-прохода | движок (`SCNLight.castsShadow`) | движок умеет это без потери баланса — прецедент: у сокурсника карта теней тоже была от движка |
| Модель освещения — как читаются свет и тень, диффузная+зеркальная составляющая | **вручную** (custom lighting-model shader modifier) | заменяет стандартную модель отражения движка — здесь и находится «рисовал самостоятельно» из примера руководителя |
| Сияние — процедурный синтез занавесов | **вручную полностью** (`AuroraSynthesis`, Strategy: основания — CPU, заполнение сетки — compute-шейдер Metal) | ядро темы курсовой |
| Сияние — объёмный рендер (ray march) | **вручную полностью** (`SCNProgram`) | ядро темы курсовой |
| Подсветка сцены сиянием | **вручную полностью** (в том же custom lighting-model modifier, источники — свой массив, не `SCNLight`) | ядро темы курсовой |

Итого движку отдано ровно то, что не является содержанием работы (геометрия окружения,
навигация, техническая генерация карты теней); всё, что составляет тему — синтез, объёмный
рендер, само уравнение освещения и то, как в него подмешивается тень и свечение — написано
руками.

## Механизм: как получить тень от движка, но освещение — вручную (проверено по документации Apple)

У SceneKit есть слоёная система кастомизации шейдера: geometry → surface → **lighting
model** → fragment (`SCNShaderModifierEntryPoint`), каждый слой можно переопределить, не
трогая соседние. `lightingModel` выполняется один раз на каждый активный источник света в
кадре и оперирует двумя структурами (дословно из документации Apple; в Metal те же поля,
`vec3`/`vec4` → `float3`/`float4`):

```glsl
struct SCNShaderLightingContribution {
   vec3 ambient;
   vec3 diffuse;
   vec3 specular;
} _lightingContribution;

struct SCNShaderLight {
   vec4 intensity;   // цвет вклада света — при forward-тенях уже с учётом тени
   vec3 direction;   // направление от точки поверхности к источнику (L), view space
} _light;
```

плюс структура предыдущего слоя `surface` (доступна и здесь):

```glsl
struct SCNShaderSurface {
   vec3 view; vec3 position; vec3 normal; vec3 tangent; vec3 bitangent;
   vec4 ambient; vec4 diffuse; vec4 specular; vec4 emission; vec4 multiply;
   vec4 transparent; vec4 reflective;
   float shininess; float fresnel;
   // + пары *Texcoord для каждого vec4-текстурного свойства
} _surface;
```

Модификатор читает `_light`/`_surface` и сам пишет в `_lightingContribution.diffuse`/
`.specular` (матовая составляющая — из `_light.intensity` и `dot(normal, direction)`,
зеркальная — по схеме Блинна-Фонга через `_surface.view` и `_surface.shininess`, оба с
коэффициентами из файла описания сцены) — стандартная модель отражения SceneKit в этом
вообще не участвует.

**Важный нюанс, найденный в документации `SCNShadowMode`:** тень попадает в
`_light.intensity` только при `shadowMode == .forward` — тогда SceneKit «рендерит тени во
время вычисления освещения», то есть встраивает результат сравнения с картой теней в
`intensity` до того, как управление переходит в модификатор. Это значение по умолчанию с
macOS 10.10, но его стоит выставлять явно и один раз обосновать в РПЗ — это и есть тот самый
баланс «карта теней от движка, использование тени в уравнении освещения — своё», по образцу
сокурсника. У `.deferred` тень накладывается отдельным постпроцессом уже после
`lightingModel` — в этом режиме модификатор её вообще не увидит, то есть это была бы уже
более «движковая» конфигурация, не наша.

Один и тот же модификатор используется и на ландшафте, и на всех пяти объектах — иначе тени
на ландшафте не появятся вообще (если ландшафт останется на стандартной модели отражения, а
объекты — на кастомной, это будут две разные, несогласованные картинки).

**Честная оговорка для РПЗ:** весь этот механизм (`SCNShadable`, `SCNShaderModifierEntryPoint`,
`SCNProgram`) в документации Apple помечен **Deprecated** на всех платформах (числится
доступным по факту до текущей версии SDK, Apple продвигает переход на RealityKit). Для
курсовой это не блокер — API работает, задокументирован и даёт ровно тот уровень ручного
контроля над освещением/тенями/сиянием, который требует руководитель; у RealityKit такого
низкоуровневого доступа к освещению нет. Но к вопросу об этом на защите стоит быть готовым
заранее, а не наткнуться на него врасплох.

## Модули

```
ParameterStore   — единственный источник правды по всем пользовательским значениям
       │
       ├─▶ AuroraSynthesis (протокол + одна активная реализация)   [вручную]
       │        │
       │        ▼
       │   плотность/цвет занавесов на общей 3D-сетке (AuroraGrid)
       │        │
       ├─▶ Terrain (SCNGeometry из карты высот)             [движок]
       ├─▶ SceneObject × ≥5 (SCNSphere/SCNBox/...)           [движок]
       │        │                              ▼
       │        │                    Aurora-нода: SCNProgram,
       │        │                    полный ray march по AuroraGrid   [вручную]
       │        ▼
       │   общий custom lighting-model modifier                [вручную]
       │   (диффуз+зеркало+тень движка+источники сияния)
       │        │
       │        ▼
       │                  кадр в SCNView / SceneView
       │
       └─▶ SwiftUI-панель (текстовые поля/слайдеры) — читает и пишет ParameterStore напрямую

CameraController — узел камеры + встроенный контроллер SceneKit          [движок]
ResearchHarness  — фиксированная сцена, перебор шага интегрирования и
                    размера сетки, замер времени кадра, CSV              [вручную]
```

### `AuroraSynthesis` — точка замены метода (без изменений в подходе)

**Где считается (решение от 2026-10-17, вариант B):** основания занавесов (шум Перлина,
не более 256 точек × 8 занавесов) — на CPU, в Swift; заполнение расчётной сетки по
основаниям — compute-шейдером Metal в 3D `MTLTexture`. Полный CPU-проход по сетке
256×256×128 (≈8,4·10⁶ узлов × до 8 занавесов, ~(3–7)·10⁹ операций) каждый кадр не даёт
реального времени; отказаться от сетки и считать плотность прямо в ray march нельзя — сетку
требует задание, и на её размере построено исследование. Compute-проход кодируется в
собственный command buffer из `renderer.commandQueue` в
`renderer(_:willRenderScene:atTime:)`, текстура отдаётся материалу аврора-ноды через
`SCNMaterialProperty`.

Прежняя CPU-сигнатура протокола больше не подходит и **подлежит пересмотру на этапе
проектирования** (конкретный вид — решение автора):

```swift
// устарело: заполнение сетки на CPU
protocol AuroraCurtainSynthesizing {
    func fillGrid(_ grid: inout AuroraGrid, curtains: [CurtainParameters], time: TimeInterval)
}
```

`AuroraGrid` — общая 3D-структура (максимум 256×256×128), теперь — 3D-текстура на GPU,
которую дальше без изменений читает аврора-нода. Открытый вопрос: что хранить в узле.
Цвет у каждого занавеса свой (три зоны), поэтому при перекрытии занавесов нужен либо цвет в
узле (RGBA16F — 64 МБ на максимальной сетке), либо номер занавеса. `CurtainParameters` —
высота границ, протяжённость, складчатость, seed, три цвета (низ/середина/верх) — на каждый
из восьми возможных занавесов.

Правило прежнее: **ничего за пределами этого модуля не должно знать, какая конкретно
реализация `AuroraCurtainSynthesizing` активна.** Аврора-нода и GUI работают только с
протоколом и с `AuroraGrid`. Кандидаты реализаций — `NOTES.md`.

### Аврора-нода — объёмный рендер сияния (`SCNProgram`, вручную)

Отдельная геометрия-контейнер (например, ограничивающий объём на все занавесы), материалу
которой назначен `SCNProgram` — полная замена вершинного и фрагментного шейдера, SceneKit
здесь не считает освещение вообще, только передаёт матрицы камеры/проекции и берёт на себя
сам draw call. Фрагментный шейдер трассирует луч через `AuroraGrid` и интегрирует
излучение-поглощение вдоль луча (без рассеяния — оно не требуется). Длина шага
интегрирования и размер сетки — ровно те параметры, зависимость времени кадра от которых
нужно исследовать (`ResearchHarness`).

### Общий custom lighting-model modifier — свет, тень, подсветка сиянием (вручную)

Один модификатор, подключённый к материалам ландшафта и всех пяти объектов:

- направленный источник (направление/цвет/интенсивность — из `ParameterStore`) с уже
  готовой от движка тенью — диффузная+зеркальная составляющая (коэффициенты из файла
  описания сцены) считаются в модификаторе, не стандартной моделью движка;
- подсветка сиянием — каждый кадр основание каждого активного занавеса делится на участки
  (по четыре на занавес, m ≤ 32), каждый участок — точечный источник (позиция центра
  яркости, интенсивность, средний цвет, **размер участка**). Источники передаются в шейдер
  своим массивом (буфер/текстура), а **не** заводятся как `SCNLight`: по документации Apple
  SceneKit «only uses up to eight light sources per node when rendering, ignoring any
  additional lights» (при 8 занавесах + направленном источнике лишние молча пропадут), а
  `castsShadow` работает только для `spot`/`directional`. Сумма по источникам — формула
  подсветки сиянием из РПЗ с множителем видимости $S_j = 1$ (тени от сияния не строятся,
  см. `SPEC.md`). Учесть, что `lightingModel` вызывается один раз на каждый `SCNLight` —
  где именно в модификаторе считать сумму, решает автор.
- **задел на тени от сияния** (если потребует руководитель): вклад сияния — отдельной
  функцией с множителем видимости, размер участка хранится для ширины полутени. Сами тени —
  мягкие (PCSS: теневая карта на участок в `texture2d_array`, поиск блокеров, PCF с ядром
  $w_p = w_L (d_r - d_b)/d_b$), на своих проходах глубины Metal внутри SceneKit — ровно тот
  же механизм «свой проход в `renderer(_:willRenderScene:atTime:)`», что и для заполнения
  сетки.

### `Terrain` и `SceneObject` (геометрия — движок, шейдинг — общий вручную-модификатор)

- `Terrain`: карта высот (grayscale-изображение) → `SCNGeometry` с нормалями, средствами
  SceneKit. Загрузчик карты высот — отдельная маленькая функция, чтобы её можно было
  заменить, не трогая построение геометрии. Материал — цвет снега и коэффициенты отражения
  из файла описания сцены, шейдинг — тот же общий lighting-model modifier.
- `SceneObject`: не менее пяти объектов из стандартных тел SceneKit
  (`SCNSphere`/`SCNBox`/`SCNCylinder`/`SCNCone`/`SCNTorus`), полигональная аппроксимация —
  параметр тесселяции самого примитива. Материал — тот же lighting-model modifier с
  коэффициентами отражения из файла описания сцены (подбирает автор, пользователь их не
  меняет — см. `SPEC.md`). Список объектов на сцене —
  данные (массив описаний: тип/трансформ/материал), а не россыпь вызовов в коде.

### `ParameterStore`

Без изменений в подходе: один `@Observable`-объект со всеми пользовательскими значениями
(полный список — `SPEC.md`; коэффициенты отражения сюда не входят, они из файла описания
сцены), SwiftUI-панель читает/пишет его напрямую, рендер на каждый кадр читает его же.

### `CameraController` (движок)

Узел камеры + встроенный `SCNCameraController` SceneKit (или `allowsCameraControl` на
`SCNView`/`SceneView`) — орбита мышью, зум скроллом. Положение наблюдателя из текстовых
полей ТЗ — прямая запись в трансформ узла камеры из `ParameterStore`, средствами SceneKit,
без ручной математики камеры.

### `ResearchHarness` (вручную)

Без изменений: фиксированная сцена, перебор (шаг интегрирования × размер сетки), замер
времени кадра через колбэки `SCNSceneRendererDelegate` (`renderer(_:updateAtTime:)` и т.п.),
дамп в CSV. Анализ и графики — вне приложения.

## Threading

Рендер живёт в колбэках `SCNSceneRendererDelegate` вместо самодельного `MTKViewDelegate` —
проще завести, поведение то же самое: один поток на кадр, GUI и ввод — main. Усложнять
структурированной конкурентностью сверх необходимого не нужно — это курсовая на 14 недель, а
не полигон на отработку конкурентности (тот отдельно есть в `future-projects`).
